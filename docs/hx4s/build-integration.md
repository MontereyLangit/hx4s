# Build integration

## 1. Current state of 3ch

### 1.1 Commands

| Command | Content | sbt starts |
| --- | --- | --- |
| `npm run v6:generate` | `sbt codegen/run` (`GenerateAppFiles.main`) | 1 |
| `npm run v6:build:client` | `vite build --mode client` | 1 (`bbsClient/fullLinkJSOutput`) |
| `npm run v6:build:server` | `vite build --mode workers` | 2 (`bbs/fullLinkJSOutput` → `bbsClient/fullLinkJSOutput`, sequentially) |
| `npm run v6:build` | The three above in order | 4 in total |
| `npm run pretest` | `sbt bbs/Test/fastLinkJS bbsClient/fastLinkJS` | 1 |
| `npm test` | `node --test tests/*.test.js` | — |
| `sbt test` | munit (common JVM / JS, bbs, bbsClient, codegen) | — |

The time per sbt start was not measured in this investigation. `docs/client-build-review.md` records 11.39 seconds for the client and 14.61 seconds for the server
(including startup, compilation and linking), but these are not before/after comparison measurements.

In 3ch at the reference commit `875a47b`, `IslandComponents.scala` is generated under `src_managed` by `bbs`'s `Compile / sourceGenerators` (`generateIslandComponents` in `build.sbt`)
calling `GenerateAppFiles --island-components`. It is not in the source tree, so it is generated by compiling `bbs` even right after a clone
(it used to be generated into the source tree; open question U-9 is decided). On the TS side, `app/routes` and `app/islands` are generated with `npm run v6:generate` and kept under Git.

### 1.2 Two-mode build

`vite.config.ts` returns two settings depending on `mode`.

| Mode | Plugins | Entry | Output |
| --- | --- | --- | --- |
| `client` | `tailwindcss()`, `scalaProject("bbsClient")` | `./app/client.ts` | `dist/static/client.js`, `dist/static/assets/*`. `emptyOutDir: false` |
| `workers` | `honox({ islandComponents: { reactApiImportSource: "react" } })`, `buildCloudflareWorkers({ external: ["cloudflare:workers"], entryContentAfterHooks })`, `scalaProject("bbs")`, `scalaProject("bbsClient", "scalajs-client")` | `app/server.ts` (HonoX default) | `dist/index.js` |

In workers mode, `scalajs:client.js` is aliased to `scalajs-client:client.js` and resolved by the second Scala.js plugin (`uriPrefix: "scalajs-client"`).
The `scalajs:` prefix belongs to the first plugin (`bbs`), so an alias is needed to read the client output under the same prefix.

`@scala-js/vite-plugin-scalajs` uses `fastLinkJSOutput` only when `mode === "development"`, and `fullLinkJSOutput` otherwise.
Neither `client` nor `workers` is development, so both use fullLinkJS.

### 1.3 Serializing `buildStart` in `scalaProject`

```ts
function scalaProject(projectID: string, uriPrefix?: string): Plugin {
  const plugin = scalaJSPlugin({ cwd: scalaCwd, projectID, uriPrefix });
  // wrap buildStart in { sequential: true, handler }
}
```

Rollup runs each plugin's `buildStart` in parallel by default. The `buildStart` of `@scala-js/vite-plugin-scalajs` starts `sbt --batch "print <project>/fullLinkJSOutput"`
as a child process, so in workers mode two sbt instances would start for the same build at the same time. `sequential: true` prevents this.

`vite.config.ts` has no comment explaining why it is serialized. KB-27 in `docs/既知不具合台帳.md` (known issues log) mentions "avoiding simultaneous sbt starts",
presumably because starting sbt in parallel in the same directory causes conflicts over the server, locks and `target/` (a guess).
`tests/islands-bridge.test.js` checks `buildStart.sequential === true` for both plugins.

`@scala-js/vite-plugin-scalajs` uses the **last line** of sbt's standard output as the output directory. It breaks if sbt prints a warning or anything else last.
On Windows it starts with `spawn("sbt.bat", args.map(x => \`"${x}"\`), { shell: true })`.

### 1.4 Test loaders

`sbt test` and parts of `npm test` run Scala.js link outputs on Node. It is neither Workers nor Vite, so the following resolutions are replaced with module hooks.

| Specifier | Replaced with | Reason |
| --- | --- | --- |
| `cloudflare:workers` | `bbs/test-stubs/cloudflare-workers-stub.mjs` | DO classes are always exported, so the import ends up in the test link output too (3ch-specific) |
| `scalajs:client.js` | `$CH3S_CLIENT_JS_DIR/client.js` | `IslandComponents` imports the client output. `Test / jsEnv` in `build.sbt` runs `bbsClient/fastLinkJS` first and passes it |
| `hono/jsx` and `hono/jsx/jsx-runtime` from inside HonoX | `react` and `react/jsx-runtime` | Reproduces the replacement Vite's `reactApiImportSource` does in production |

Tests in `npm test` that use Vite (`islands-hydration`, etc.) do the same with Vite's `resolve.alias` and the `islandComponents()` plugin instead of a loader.

### 2.0 The only combination verified in P0

Changing only one side of the setting keys (`hx4sAppDir`, `hx4sServerModuleId`, etc.) and the fixed values on the Vite / HonoX side causes mismatches.

| Fixed value | Where |
| --- | --- |
| Route discovery `/app/routes`, island discovery `/app/islands` (`import.meta.glob` has `/app` fixed) | HonoX (`server/with-defaults.js`, `client/client.js`) |
| The value of `component-name` = the absolute path from the Vite root (`/app/islands/x.tsx`) | HonoX (H3) and `islandIdPrefix` in `AppFileRenderer.islandComponents` |
| Virtual module name `scalajs:<moduleID>.js`, and `scalajs-client:` for reading the client | `vite.config.ts` (hx4s-vite) and `CodegenConfig.virtualModulePrefix` |

P0 treats the following as **the default and the only verified combination**. Anything else is "not verified"; either reject it or use it at your own risk.

- appDir is `app` (`app/routes`, `app/islands`).
- moduleIDs are `server` for the server and `client` for the client.
- The virtual module prefix is `scalajs:` (with the alias `scalajs-client:` when the server build reads the client).

Making these configurable needs a common setting that passes the same value to both codegen and hx4s-vite. It isn't created in P0 and is an open question for P1 ([roadmap.md](roadmap.md) U-18, U-25).
Even when sbt-hx4s's setting keys (2.2) accept values other than these defaults, P0 doesn't verify non-default values. Write "not verified" until integration tests with non-default values are added.

### 2.1 The hx4s-vite API (implemented in Phase 3)

```ts
import { defineConfig } from "vite";
import hx4s from "hx4s-vite";
import buildCloudflareWorkers from "@hono/vite-build/cloudflare-workers"; // the user's choice

export default defineConfig(({ mode }) => {
  const plugins = hx4s({
    mode,                         // "client" | anything else (server)
    sbt: { cwd: import.meta.dirname },
    server: { projectID: "server" },                       // default
    client: { projectID: "client", entry: "./app/client.ts" }, // defaults. module, uriPrefix and output can be changed too
    honox: {},                    // extra options passed as-is to honox()
  });
  return mode === "client"
    ? { plugins, build: { outDir: "dist/client" } }
    : { plugins: [...plugins, buildCloudflareWorkers({ outputDir: "dist/server" })] };
});
```

- The return value is `PluginOption[]`. In client mode, it returns the client Scala.js plugin and a plugin whose `config` hook adds the output names (`static/client.js`, `static/assets/*`) and `emptyOutDir: false`.
  The output names can be overridden individually with `entryFileNames`, `chunkFileNames` and `assetFileNames` of `client.output` (the defaults are the fixed names above).
  Hashed entry names (`client-[hash].js`) are not the default, because how to pass the name referenced from the HTML is undecided ([roadmap.md](roadmap.md) U-26).
  While names are fixed, version skew between the HTML and the client is detected by the validation in `hx4s-vite/client`, which stops hydration ([rendering-model.md](rendering-model.md) 2.4).
  In server mode, it returns `honox()` (with `islandComponents.reactApiImportSource` defaulting to `"react"`), the server and client Scala.js plugins, and the alias `scalajs:client.js` → `scalajs-client:client.js`.
- The `mode` name (`client`) matches the check in HonoX's `honox-vite-client` (`mode === "client"`).
- The Scala.js plugin uses `@scala-js/vite-plugin-scalajs` as-is, adding only the serialization of `buildStart` (exported as `scalaProject()`). It is not forked.
- `hx4s-vite/client` has a small function, `islandPropsProblem(element)`, used from the client entry (`app/client.ts`). It walks the element to hydrate and its element props (children HonoX restores from templates),
  and returns the first mismatch reported by the validation function `hx4sValidate` attached by `hx4s.react.IslandExport`. It doesn't wrap the options of HonoX's `createClient`; they are written in the template as-is ([rendering-model.md](rendering-model.md) 2.4).
  It doesn't import the main `hx4s-vite` (the Vite plugin), so Vite and HonoX's SSR code don't end up in the client bundle.
- The Node loader is `hx4s-vite/node-register` (passed to `--import`). It resolves `scalajs:client.js` to `HX4S_CLIENT_JS_DIR/client.js`, and `hono/jsx` inside honox to `react`.
  The loader itself is exported as `hx4s-vite/node-loader` and can be registered alongside the user's loader (2.3).
- peerDependencies list only verified versions (`honox` 0.1.62, `@scala-js/vite-plugin-scalajs` 1.1.0, `vite` ^8.3.3). vite-plugin-scalajs has vite as a `"4.1.4 - 7"` dependency, so users specify `"vite": "$vite"` in `overrides` ([compatibility.md](compatibility.md) 1.3).

### 2.2 sbt-hx4s settings (implemented in Phase 3)

```scala
// project/plugins.sbt
addSbtPlugin("io.github.montereylangit" % "sbt-hx4s" % "<version>")

// build.sbt
lazy val server = project.enablePlugins(ScalaJSPlugin, Hx4sPlugin).dependsOn(shared)
  .settings(
    hx4sClientProject := client,
    libraryDependencies += "io.github.montereylangit" %%% "hx4s-react" % hx4sVersion,
  )
```

Users write only `enablePlugins(Hx4sPlugin)` and `hx4sClientProject`; everything else works with the defaults. There is one AutoPlugin, `Hx4sPlugin`, enabled on the server project
(the Phase 0 proposal's `Hx4sServerPlugin`, and `hx4sServerMain` / `hx4sClientMain` / `hx4sMainObject` specifying sources one file at a time, were not adopted.
Codegen reads top-level objects regardless of their names, so passing all of the project's Scala sources is enough).

| Key | Default | Description |
| --- | --- | --- |
| `hx4sClientProject` | None | The client project with `@islands`. The default source of `hx4sClientSources`. If not set, the setup is treated as client-less (SSR only), and `IslandComponents` is an empty object |
| `hx4sServerSources` / `hx4sClientSources` | `Compile / unmanagedSources` (`.scala`) of this project / `hx4sClientProject` | Source files whose annotations are read |
| `hx4sProjectRoot` | `ThisBuild / baseDirectory` | Base of generation (Vite's root). Source paths are passed to codegen relative to it, and error messages show these relative paths |
| `hx4sRouteDir` / `hx4sIslandDir` | `<root>/app/routes` / `<root>/app/islands` | Output directories |
| `hx4sIslandIdPrefix`, `hx4sServerModule` / `hx4sClientModule`, `hx4sVirtualModulePrefix` | `/app/islands/`, `server` / `client`, `scalajs:` | The fixed values of 2.0. When changing them, match the hx4s-vite and HonoX sides too (not verified) |
| `hx4sIslandComponentsPackage` / `hx4sIslandComponentsObject` | `hx4s.generated` / `IslandComponents` | Names of the generated Scala |
| `hx4sIslandBridge`, `hx4sIslandExportType`, `hx4sAnnotationPackage` | `hx4s.react.Island`, `hx4s.react.IslandExport`, `hx4s.annotation` | hx4s names referenced by generated files |
| `hx4sBanner` / `hx4sGeneratedMarker` | Empty / `None` (codegen's defaults) | First lines of generated files |
| `hx4sCodegenVersion` | Same as the plugin | Version of `hx4s-codegen_3` to resolve |
| `hx4sCodegenJavaOptions` | Empty | Options for the JVM running codegen |
| `hx4sVersion` (value) | The plugin's version | Used for the `hx4s-core` / `hx4s-react` dependencies |
| `hx4sCheckDependencies` | task | Checks that the client (and its transitive `dependsOn`) doesn't depend on a project with `Hx4sPlugin` enabled, and that this project doesn't depend on the client. On violation, prints the path (e.g. `client -> mid -> server`) and fails. Called first by `hx4sGenerate` and `hx4sIslandComponents` |
| `hx4sGenerate` | task | Generates route / island TS and returns the files generated this time (or kept because their content was identical). The list is read from codegen's `--output-list`; the plugin doesn't hold the generated marker |
| `hx4sIslandComponents` | task | Generates `IslandComponents.scala` in `Compile / sourceManaged`. Registered in `Compile / sourceGenerators`. Doesn't start codegen when inputs are unchanged ("Incremental key" below) |

`hx4sCheckDependencies` looks at classpath dependencies in `buildDependencies`, following only those whose configuration on the left side of `dependsOn` is `compile` / `runtime` (including none).
Test-only dependencies such as `dependsOn(x % "test")` are excluded. The server depending on the client is also rejected because the client implementation must not go directly into the server bundle,
and only goes through the virtual module `scalajs:client.js` ([module-boundaries.md](module-boundaries.md) chapter 2).

The incremental key (of `hx4sIslandComponents`) is the content of the client sources, the arguments to codegen, `javaHome`, `hx4sCodegenJavaOptions`, and the order of the codegen classpath plus hashes of each JAR's content (for a directory, the files inside it).
It regenerates when a SNAPSHOT JAR at the same path is replaced, and when JVM settings change. JVM settings often don't affect the output, but including them in the key costs at most one extra regeneration, so they are included.
`hx4sGenerate` doesn't cache and starts codegen every time (identical content isn't written, so the output's modification times don't change).

Details of the setting keys and their mapping to codegen arguments are under "Settings" in [codegen.md](codegen.md).

### 2.3 Registering the Node loader alongside the user's loader

`hx4s-vite/node-register` registers only hx4s's loader (`scalajs:client.js` and `hono/jsx` inside HonoX). Users who need a loader that points runtime specifiers (such as `cloudflare:workers`)
to test stubs register both in their own register file instead of `node-register`.

```js
// test-stubs/register.mjs (user)
import { register } from "node:module";

register("hx4s-vite/node-loader", import.meta.url);   // scalajs:client.js, hono/jsx inside honox
register("./runtime-loader.mjs", import.meta.url);    // runtime stubs
```

```js
// test-stubs/runtime-loader.mjs (user)
export async function resolve(specifier, context, nextResolve) {
  if (specifier === "cloudflare:workers") {
    return { url: new URL("./cloudflare-workers-stub.mjs", import.meta.url).href, shortCircuit: true };
  }
  return nextResolve(specifier, context);
}
```

- The loader registered last is called first and proceeds to the previous loader with `nextResolve`. The specifiers handled by hx4s's loader and the user's loader don't overlap, so the order doesn't matter.
  When both handle the same specifier, the one registered last wins.
- The specifier in `register("hx4s-vite/node-loader", import.meta.url)` is resolved from the location of the register file, so `node_modules/hx4s-vite` must be visible from there.
- Passing two `--import`s (`--import hx4s-vite/node-register --import ./test-stubs/register.mjs`) also works.
- This setup is checked by `tests/node-loader.test.js`.

In sbt's `Test / jsEnv`, link the client first, pass `HX4S_CLIENT_JS_DIR`, and specify your own register file for `--import`.

```scala
// build.sbt (the user's server project)
import org.scalajs.jsenv.nodejs.NodeJSEnv

Test / jsEnv := {
  val clientDir = (client / Compile / fastLinkJS / scalaJSLinkerOutputDirectory).value
  (client / Compile / fastLinkJS).value
  new NodeJSEnv(
    NodeJSEnv.Config()
      .withArgs(List("--import", (baseDirectory.value / "test-stubs" / "register.mjs").toURI.toString))
      .withEnv(Map("HX4S_CLIENT_JS_DIR" -> clientDir.getAbsolutePath))
  )
}
```

When passing a file path to `--import`, use `toURI.toString` (a `file:` URL). On Windows, `C:\...` as-is is read as a URL scheme and fails.
If hx4s's loader alone is enough, `--import hx4s-vite/node-register` as in `examples/minimal/build.sbt` works (the specifier is then resolved from Node's working directory).

## 3. Comparison of codegen approaches

### 3.1 Generation approach

| Approach | Pros | Cons | Decision |
| --- | --- | --- | --- |
| scalameta syntax analysis (current) | Runs before compilation. TS files can be output before Vite. Small implementation (the current `AnnotationScanner` is about 175 lines). Runs on the JVM, so fs handling is straightforward | Can't resolve types. Can't follow import aliases or type aliases. Arguments are limited to string literals | **Adopted** ([ADR 0004](adr/0004-scalameta-codegen.md)) |
| Scala 3 macros | Can resolve types. Can check the contents of props too | Writing files during compilation is a side effect. Making TS files depend on Scala compilation results complicates the Vite → sbt → Vite ordering. Using the JVM fs during Scala.js compilation is outside the intended use of macros | Keep the idea of adding only type checks with macros in P2 |
| sbt source generators (generating inside sbt itself) | Fits naturally into sbt's task graph | sbt 1.x is Scala 2.12. A generator written in Scala 3 can't run as-is. If the generator is written in 2.12, parsing users' Scala 3 syntax (`enum`, optional braces) is possible with scalameta dialects, but there would be two lines of the generator | Used as the entry point for calling (connect `hx4sGenerate` to `sourceGenerators`). The generator itself is separate |
| A compiler plugin | Type information unified with compilation | Scala 3 compiler plugins depend on unstable APIs and are heavy to maintain across versions | Not adopted |

### 3.2 Running from sbt

`hx4s-codegen` runs on Scala 3, and sbt 1.x plugins run on Scala 2.12. Current 3ch makes `codegen` a subproject of the same build and calls it with `runMain`,
but users' builds can't be expected to have a generator subproject.

The approach is "resolve `hx4s-codegen_3` in a dedicated configuration and call main with that classpath in a separate class loader or a fork".

- **The scalafmt approach** (sbt-scalafmt / scalafmt-dynamic): fetch the artifact of the specified version at run time and load it in an isolated class loader.
- **The ScalaPB approach** (sbt-protoc / protocbridge): run artifacts resolved in a dedicated configuration in isolation, so that the generator can run on a different Scala version.

P0 prioritizes simplicity of implementation and uses a **fork** (`java -cp <resolved> hx4s.codegen.CodegenMain <args>` with `Fork.java`). It starts one extra JVM,
but there's no need to think about separating class loaders (conflicts between the Scala 2.12 and 3 standard libraries). If the startup cost becomes a problem, switch to an isolated class loader within the same JVM.

The Phase 3 implementation:

- `hx4s-codegen_3` is a `libraryDependencies` entry of the dedicated configuration `hx4s-codegen` (`hide`), and the classpath is taken from the result of `update` (`hx4sCodegenClasspath`).
- Settings are passed as a sequence of `--key value` arguments rather than JSON (the form `CodegenMain` accepts; the same as calling without sbt). Arguments are passed to `ProcessBuilder` without a shell, so paths containing spaces or `[]` pass through as-is.
  Sources are passed one file at a time by repeating `--server-sources` / `--client-sources`, and codegen doesn't split on commas (a path containing a comma is one path).
- Output of the forked JVM goes to sbt's logger. If the exit code is non-zero, the `[hx4s-codegen] error: <path>:<line>: <reason>` lines are collected and included in the task's failure message.
- Codegen doesn't run in sbt's own JVM (so `System.exit` and loading Scala 3's standard library don't affect sbt).
- Verified by the scripted tests in `sbt-plugin/src/sbt-test/hx4s/` (`generate`: generation, regeneration, deleting stale generated files, deleting the last island, sources containing commas and spaces, client-less setups, `sourceGenerators`;
  `error`: failure and line numbers with wrong annotations; `dependencies`: failure and the path for the forbidden dependencies client → server and server → client).

Moving to sbt 2.x (Scala 3) would likely allow calling it in the same class loader, but the timing of moving to an official sbt 2 release is unpredictable, so it isn't assumed (U-10).

### 3.3 Output rules for generated files

Based on 3ch's `codegen/.../framework/OutputWriter.scala` and `OutputPath.scala` (`875a47b`), P0 satisfies the following. "Current" refers to the implementation at `875a47b`.

| Rule | Current (`875a47b`) | P0 |
| --- | --- | --- |
| Deterministic output (ordering, line endings) | Routes sorted by path, islands in declaration order. Line endings are `\n` | Same. Island order is also fixed to declaration order |
| Don't rewrite identical content | Yes (`sameContent`; line ending differences are ignored) | Same. Comparison is done after normalizing line endings to `\n` (so that LF/CRLF differences from Windows' `core.autocrlf=true` don't cause rewrites every time) |
| Never overwrite or delete files without the generated banner | Yes (whether the first line starts with `generatedMarker`) | Same. The default prefix is `// This file is generated by hx4s-codegen`. Migrating from an old banner is done not by accepting several markers built in, but by the user setting `hx4sBanner` / `hx4sGeneratedMarker` to the old values (a Phase 3 decision; [codegen.md](codegen.md)) |
| Finish all checks before writing | Yes (`plan` collects errors, and nothing is written if there is even one) | Same |
| Reject writes outside the output root | Segment checks (`..`, reserved names, character classes), and checking that the lexically normalized path is under the output root | Same. Links are handled separately under "Link policy" below |
| Detect conflicts differing only in case | Yes (among outputs, and against existing files and directories) | Same (because NTFS / APFS default to case-insensitive) |
| Delete stale generated files | Only regular files with the banner under `routes/` and `islands/` (`walkFiles` excludes links) | Same. `IslandComponents` is left to sbt's `src_managed` |

#### Execution order, and what isn't guaranteed

**The state at Phase 0** (`OutputWriter.write`): the order was check → delete stale generated files → write files with different content with `Files.write`. No replacement through temporary files.
Since deletion came before writing, a failure during writing could leave the old generated files gone and only some of the new ones present. hx4s-codegen fixes this to the order in the policy below.

**P0 policy**: this document doesn't use the word "atomic", and guarantees only the following.

- Guaranteed: writing starts only after all checks pass. Identical content isn't written.
- Not guaranteed: atomicity across multiple files (a failure midway can leave TS and Scala at different generations), mutual exclusion of concurrent runs (the result of running two generations at the same time).

The execution order is **new writes → delete stale generated files** (the reverse of the current one). If writing fails, the stale generated files aren't deleted.
Even after a failure midway, the recovery method is that **rerunning converges** (generation is deterministic, identical content isn't written, and remaining stale files are deleted next time).
Per-file replacement (writing to a temporary file and then `Files.move`) may be adopted so that no single file is left half-written, but it doesn't guarantee consistency across files.
It was adopted in the Phase 3 review (K2): with direct `Files.write`, a failure after truncating an existing file would lose the generated marker, the next run would treat the file as hand-written, and it wouldn't converge.

Verification conditions: after a failure midway through writing (failure injection), rerunning converges to the expected state. Concurrent runs are out of scope, so verification is limited to "the scope written in the documentation".

#### Link policy (symlinks / Windows junctions)

**Policy**: the generator **doesn't follow output links, and rejects them**. This is defined for each of the following four places.

| Target | Policy |
| --- | --- |
| Output roots (`app/routes`, `app/islands`, the output directory in `src_managed`) | Reject if the root itself is a link (symlink / junction) |
| Intermediate directories of output paths | Reject if a link (existing directories must not be links) |
| Leaf files | Reject if the existing one is a symlink (`Files.write` follows links and writes outside) |
| Deletion targets | Never delete links (keep `!Files.isSymbolicLink` in `walkFiles`; junctions are detected the same way) |

**Status**: implemented (added in the original project's Phase 1 and moved to hx4s-codegen in Phase 3). Detection uses `isSymbolicLink || isOther` of `Files.readAttributes(path, BasicFileAttributes, NOFOLLOW_LINKS)`
(Java returns junctions as `isSymbolicLink=false`, `isOther=true`). Searching for stale generated files doesn't use `Files.walk`; it walks on its own and treats any link as an error.
In the Phase 3 review (K1), ancestors leading to the output root (below `projectRoot`; e.g. `app` is a junction while `app/routes` is a regular directory) are rejected too.
`projectRoot` itself and above are out of scope ("Output rules" in [codegen.md](codegen.md)).
The execution order is "delete leftover temporary files and stale generated files that differ only in case → write through temporary files → delete the remaining stale generated files". The negative tests below are in `OutputWriterSuite`.
On Windows locally, the junction tests pass, and the symbolic link tests are skipped with `assume` for lack of permission to create them (they run in Linux CI).

Negative tests (verification conditions): in the following cases, nothing is written outside, nothing is deleted, and an error occurs. On Windows, check the junction tests locally (skipping is allowed in environments where creating symlinks requires permission).

1. The output root is a link to an external directory.
2. An intermediate directory of an output path is a link to the outside.
3. An existing leaf file is a symlink to an external file.
4. When there is a link to the outside inside a managed directory, deleting stale generated files doesn't delete the link target.
5. The same as 1–2 with directory junctions (Windows).
6. An ancestor of the output root (below `projectRoot`) is a link to the outside (both symlink and junction).

## 4. Comparison of CLI approaches

There are situations where you want to run only generation without sbt (checks in CI, calls from a Vite plugin, on save in an editor).

| Approach | Pros | Cons |
| --- | --- | --- |
| An npm CLI (`npx hx4s generate`) that calls sbt | Easy to use from JS tools | It still starts sbt. The cost of starting sbt doesn't change |
| An npm CLI that starts the JVM `hx4s-codegen` directly (fetched with coursier, or with the jar bundled) | Doesn't go through sbt | Requires a JDK. Bundling the jar makes the npm package large. Requires users to install coursier |
| Only the sbt plugin task (`sbt hx4sGenerate`) | Minimal implementation. Version resolution is unified in sbt | Requires starting sbt |
| `hx4s-codegen`'s main directly (`cs launch io.github.montereylangit:hx4s-codegen_3:<v> -- …`) | Few dependencies | Users need to know how to use coursier |
| Distributing a codegen built with Scala.js through npm | Runs with Node alone | The availability of a Scala.js version of scalameta, and the burden of rewriting fs handling (not investigated) |

P0 provides only two: **the sbt plugin task + `hx4s-codegen`'s main (taking settings as arguments)**. An npm CLI is for P1, decided once there are more users.

### 4.1 Windows considerations

3ch's development environment is Windows, and it already has the following measures. hx4s inherits them.

- sbt is started as `sbt.bat` with `shell: true`, with arguments wrapped in `"` (vite-plugin-scalajs). Design so that arguments don't contain `"` or `%`.
- Paths passed to `runMain` escape `\` and `"` (`quotedPath` in `build.sbt`). sbt-hx4s passes `File`s directly within sbt tasks and doesn't convert them to strings.
- Paths with square brackets like `[bbs]` can collide with shell globs. The generator handles them as Java `Path`s without going through a shell.
- Line endings: generation always uses LF. Comparisons normalize (3.3).
- Conflicts on case-insensitive file systems (3.3).
- Path length: going beyond 260 characters in deep hierarchies of `app/routes` causes problems with Git for Windows and some tools (general knowledge; no record of it happening in 3ch).
